## 2026-08-07 UT harness and correction

Before another performance run, the three-voter harness reproduced the
single-group failure with 300 concurrent proposals: leader churn returned
`NotLeader` errors. `GroupHandle` now applies an eight-proposal per-group
backpressure gate, and the regression suite covers 32 concurrent proposals,
300 baseline-level proposals, membership convergence, and committed state on
all three voters. The full nine-test three-voter suite and all nine
`chirps-multi-raft-perf` unit tests pass; the loopback test was rerun with the
minimal permission needed for TCP bind.

## 2026-08-07 Multi-Raft measurement decision

The controlled local profile was rerun after adding the TiKV-compatible
comparison contract. It used one host and three logical containers; physical
three-node hardware was not required. The ten load phases completed, but the
release artifact was rejected because every single-group baseline sample timed
out (3,600 timeouts, zero commits) and the native Multi-Raft samples were far
below the declared gate. The detailed result is recorded in
`docs/release/evidence/v0.6.0/multi-raft-native-2026-08-07/RESULT.md`.

This is a genuine release blocker for the performance claim, but it is not a
physical-host blocker. The TiKV/YCSB-compatible Workload A contract is now
covered by unit tests; no RawKV/YCSB measurement is claimed because the current
runner reports quorum-committed proposals rather than READ/UPDATE OPS.

## 2026-08-07 corrected measurement after UT fix

The preflight harness passed (9/9 three-voter tests and 9/9 performance-harness

## Harness resource audit (2026-08-07)

The prior corrected run exposed a harness-side risk: Multi-Raft RSS reached
3.66 GiB while single-group RSS stayed near 20 MiB. Investigation found an
unbounded per-group Raft dispatch FIFO and an implicit 65,536-entry QUIC send
queue. The harness now uses a bounded 32-frame FIFO and an explicit 4,096-entry
send queue, with a regression test for FIFO backpressure. The 10-test harness
suite passes. Details are recorded in
`docs/release/evidence/v0.6.0/multi-raft-native-2026-08-07-fixed/HARNESS-AUDIT.md`.

Because these settings change the measurement configuration, the earlier
performance result is invalid for the corrected harness. No new performance
claim or release decision may be made until the corrected profile is rerun with
per-node RSS and dispatch/send queue depth evidence.

The bounded-profile rerun completed all ten phases but still failed final
verification on timeouts. Multi-Raft peak RSS decreased from 3.66 GiB to 1.91
GiB, while its median was only 324.45/s. High RSS remained concentrated on the
seed/leader node, so the harness is improved but not yet proven non-interfering.
See `docs/release/evidence/v0.6.0/harness-bounded-2026-08-07/RESULT.md`.

The follow-up resource audit (revision `2011052`) measured the load generators
directly: 4.6–5.4 MiB peak RSS each, versus up to 1.86 GiB in a node. Dispatch
depth was low at several node RSS peaks, and retransmission/overflow/
backpressure counters were zero. Thus harness loadgen memory is not the cause
of the remaining node RSS; the unresolved boundary is node-side Raft/WAL/log/
snapshot/allocator retention. Diagnostic evidence is recorded at
`docs/release/evidence/v0.6.0/queue-metrics-2026-08-07/RESULT.md`.

The node-side bottleneck audit corrected the WAL fallback, which had been
materializing the entire WAL for each bounded range request. The fix also
deduplicates log-cache order entries and removes an install-snapshot payload
clone. After the fix, Multi-Raft median improved from 296.72/s to 408.85/s and
maximum node RSS fell from 2.03 GiB to 1.76 GiB. Timeouts remain, including a
zero-commit sample, so this is diagnostic improvement only and release remains
BLOCKED. See `docs/release/evidence/v0.6.0/wal-range-fix-2026-08-07/RESULT.md`.

The subsequent full phase audit records all 13 boundaries for all 10 samples
(130/130), warmup/measure/drain RSS for all loadgen processes, and 239–240 node
metric points in each 60-second measurement window. The UT suite is now 14/14.
The rerun still measured only 296.72/s Multi-Raft median with 13,493 timeouts;
it is diagnostic evidence and does not change the BLOCKED release decision.
See `docs/release/evidence/v0.6.0/phase-audit-2026-08-07/RESULT.md`.

## 変更影響レビュー

- 公開 API / wire format / 永続化 / 設定 / observability への影響: #17、#19–#24 の各 spec で実装開始前に記入する。
- 既存テストで覆えない経路: deterministic network、実ディスク crash/restart、TSO leader lease、public Mesh API、複合 QUIC traffic、public-registry dependency、versioned release gates。
- 互換性・移行・rollback: v0.5 RaftNode API の API signature compatibility を維持する。v0.5 / v0.6 混在 cluster は拒否する。破壊的変更と alopex-core version は migration / SemVer 根拠を残す。
- セキュリティ・性能・実ネットワークの確認: #19–#23 が roadmap の条件と evidence を定義し、#18 のrequired-evidence catalogとtarget-version manifestが対象版だけをrelease gateへ結び付ける。不足artifactはpublish前にfail closedする。
