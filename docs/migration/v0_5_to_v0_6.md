# Migrating Chirps v0.5 to v0.6

The existing single-group `RaftNode` API remains available. Multi-Raft, TSO,
and HLC are additive, feature-gated APIs; enable only the capabilities used by
the application. A v0.5 and v0.6 node cannot form a mixed-version cluster, so
upgrade by replacing the whole cluster behind a stopped write boundary or by
building a parallel v0.6 cluster and moving traffic after validation.

## Multi-Raft

Enable `multi-raft`, create a `MultiRaftManager`, and create one group for each
former single-group deployment. The default `MultiRaftConfig` admits 100 groups.
Raising `max_groups` is explicit and should be paired with Prometheus series and
resource-capacity review. Unknown groups, duplicate creation, and a reached
limit are typed errors; they never allocate a partial storage namespace.

Before moving writes, verify each group has the intended three logical voters,
has caught up, and exposes the same applied state digest. Do not initialize
three independent one-voter clusters and call them a three-voter group.

## Metrics

Metric names now use the stable `chirps_` prefix. Replace dashboards and alerts
that query `raft_*` with the corresponding `chirps_raft_*` names and use the
provided Grafana dashboard. TSO and HLC add `chirps_tso_*` and `chirps_hlc_*`.

`serve_metrics` remains public for compatibility. Production services should
switch their HTTP handler to `serve_metrics_authorized` with a bearer policy,
and should terminate TLS at the service or ingress boundary. Never place the
bearer token in source control, logs, labels, or dashboard variables.

## Rollback

Stop writes, confirm all v0.6 groups have no unapplied committed entries, and
restore the v0.5-compatible application and data snapshot taken before the
upgrade. Do not join v0.5 processes to the v0.6 cluster. Revert metric queries
only after the v0.5 service is active; retaining the v0.6 dashboard during
rollback is harmless but yields absent series.
